# Paasta service contract

The open-source client uses a separately operated Paasta account and AI service. The service implementation, credentials and customer data are not part of this repository. Default origin: `https://console.paasta.cloud`. For a compatible local service set `PAASTACODE_CONSOLE` to an HTTPS origin or loopback HTTP origin. The client does not implement a mock account in normal operation.

- `POST /api/cli/device` with `{clientId:"paastacode",clientName:"PaastaCode"}` returns `clientId:"paastacode"`, `deviceCode`, `userCode`, `expiresIn`, `verificationUriComplete`. The client refuses older servers that do not acknowledge this client ID, before showing an authorization link. Verification must remain on the configured origin at `/cli/authorize`.
- `POST /api/cli/device/token` with `{deviceCode}` returns `{error:"authorization_pending"}` or `{token}`. Never log the device code, token or model key.
- Authenticated `GET /api/paastacode/connection` returns `{account:{id,tenantId,name,balanceToman},models:[{id,name,supported_parameters,context_length,max_output_tokens,input_toman_per_million,output_toman_per_million}]}`. The account token is sent as a Bearer header.
- Authenticated `POST /api/paastacode/connection` with `{dailyLimitToman}` returns `{key,dailyLimitToman}`. `DELETE` revokes only the requesting device's token and linked key, including a legacy or downgraded token; it never accepts a target identity from the request. The client keeps the AI key outside renderers.
- Inference uses OpenAI-compatible `/api/ai/v1` with that AI key. Prices come from Paasta and money is toman. The Go page is an editorial preference source only.
- Authenticated `GET /api/paastacode/sessions` returns `{sessions:[{id,title,revision,updated_at}]}` for the current user; `GET ?id=UUID` returns one with its snapshot. `PUT` accepts `{id,title,revision,snapshot:{version:1,messages:[{role:"user"|"assistant",text}]}}`; `revision` is zero for a new record or the last acknowledged revision. A conflict returns HTTP 409; successful writes return `{id,revision}` and are read back. `DELETE ?id=UUID` removes one.

The service must enforce user and tenant ownership, role and scope checks, bounded snapshots, encrypted storage, atomic audit, revision conflicts and idempotent key provisioning. A public client is never an authorization boundary. Account tokens must grant only the PaastaCode scopes. The backend was deployed on 2026-10-12; isolated synthetic accounts verified the public HTTPS device flow, model-key lifecycle, encrypted save/readback, retry/conflict behavior and tenant isolation under the production application role. This acceptance did not perform paid inference.

## Deployment integration

Authenticated `GET /api/paastacode/devices` returns `{devices:[{id,name,device_client_id,created_at,last_used_at,expires_at,revoked_at,current}]}` for the requesting user's PaastaCode grants in the current tenant, capped at 100. It excludes ordinary CLI/API grants, token hashes, prefixes and keys. `DELETE ?id=UUID` requires write scope and current role; an absent or foreign grant returns `{ok:true,revoked:false,current:false}`. Owned revocation atomically revokes the token, linked managed AI key and records one audit; retries do not add audit. The local broker advertises `features.deviceManagement:true` and stops execution/clears login after current-grant revocation. It attempts to revoke this local installation's separately consented deployment grant too; a network failure is reported and preserved for retry. Conversations and workspace files remain. Device listings cannot terminate another user's connection, even within the same tenant.

Individual conversation reads advertise `features.conditionalDelete:true`. The new UI must not enable deletion without this acknowledgement. Conditional deletion uses `DELETE /api/paastacode/sessions?id=UUID&revision=N` with the revision just reviewed; a newer revision returns 409 without deleting. The user lock, row lock, removal and audit are atomic. A missing or already deleted record returns `{ok:true,deleted:false}` without duplicating audit or exposing a foreign account's record. Raw `DELETE ?id=UUID` remains compatible with legacy callers. Export is an explicit browser download of `{version:1,title,messages:[{role,text}]}`; connection and tool metadata are omitted. Retention is manual deletion with a 200-record account limit; background sync is not yet enabled.

The hosted UI origin is exactly `https://code.paasta.cloud`. Local servers reject this origin unless started with `--hosted`; opted-in CORS allows only GET/POST/DELETE and Authorization/Content-Type, never cookies. Every operation still requires the per-workspace capability. The hosted asset route is a fixed allowlist and cannot expose local state, tokens or private platform APIs. Pairing stays in the URL fragment/browser session, and the fragment is cleared before API requests. Supporting browsers request loopback-network permission; denial retains the pairing form and an actionable error. This is a hosted interface to local execution, not a hosted execution service.

Deployment is a separate device connection: `clientId:"paastacode-deploy"` must be acknowledged by the server and explicitly reviewed on the Paasta authorization page. Its 30-day token grants only `paastacode:read`, `paastacode:write`, `projects:read`, `deployments:write` and `logs:read`. It must match the base account's user and tenant. `GET /api/paastacode/identity` returns only `{id,tenantId}` after current role/scope checks.

Paasta's `/api/mcp` JSON-RPC endpoint supplies the authoritative project/log/Git-deployment tools. The local stdio broker stores no credential in model configuration and turns mutations into one-use human review requests. Source upload uses the shared MIT Paasta CLI: `--dry-run --hash --json` computes the exact archive hash; approved execution passes `--source-sha256`, `--no-env`, `--no-addons` and `--detach`. A changed source or price fails closed. Deployment observation uses `/api/projects/deploy/:id`; ambiguous mutations are never automatically replayed. Resource selection for new Compose storage remains a completion gate.
