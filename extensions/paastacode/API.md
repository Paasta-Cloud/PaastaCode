# Paasta service contract

`POST /api/prompt` accepts optional `attachments: [{name,data}]`, where `data` is canonical base64 of file bytes, never a remote URL or filesystem path. An owned authenticated session and valid paid model are still required. The broker validates names, bytes, count (8), per-file (4 MiB) and total (6 MiB) bounds before modifying workflow state or calling the engine. Prompt transport is bounded to 10 MiB; other operations retain their existing limits. UTF-8 text is sent as synthetic context plus a visible filename; PNG/JPEG/GIF/WebP and PDF use engine file parts only when the selected model advertises the matching input modality. Automatic execution also requires a compatible execution model. `state.features.promptAttachments` allows new clients to reject older brokers that would ignore files. Account text backups retain attachment names, not attached bytes; restoring a cloud text backup requires attaching the original files again.

The local broker advertises `features.workspaceAccess` and `features.git`. `POST /api/access` accepts `mode:review|full`, requires the private workspace capability and a configured Paasta account, and persists the choice separately per account/workspace. Owned sessions receive the actual OpenCode permission rules; a background broker handles pending Full Access requests even without a browser. Other workspace sessions are excluded, and returning to review removes automatic approvals. These modes do not expand Paasta account scopes or deployment consent.

`GET /api/git` returns branch, upstream, ahead/behind, remote names and changed file paths. `GET /api/git/diff?path=...` accepts a path from current status. `POST /api/git` accepts only init, branch, remote, fetch, pull, push or selected-path commit. Commands use argument arrays, pull is fast-forward-only, credential-bearing remote URLs are refused, unrelated staged files remain staged, and raw Git/helper stderr is not returned. These operations require a configured account, workspace capability, valid origin and the current account epoch.

Packaged desktops expose a narrow IPC update interface (state/check/download/install/automatic); only the main application frame may call it, and the renderer cannot choose an update source. Electron updater uses the official GitHub feed. CLI/VSIX downloads require the exact official asset URL, size and GitHub SHA-256 digest. Portable CLI upgrades use a private pointer to a verified side-by-side installation, retaining the original executable and workspace files. Broker `POST /api/update/prepare` refuses busy work and pauses new broker mutations before installation; cancellation removes the pause. Release assembly verifies update metadata hashes and merges macOS architecture entries rather than overwriting one architecture's feed.

The open-source client uses a separately operated Paasta account and AI service. The service implementation, credentials and customer data are not part of this repository. Default origin: `https://console.paasta.cloud`. For a compatible local service set `PAASTACODE_CONSOLE` to an HTTPS origin or loopback HTTP origin. The client does not implement a mock account in normal operation.

- `POST /api/cli/device` with `{clientId:"paastacode",clientName:"PaastaCode"}` returns `clientId:"paastacode"`, `deviceCode`, `userCode`, `expiresIn`, `verificationUriComplete`. The client refuses older servers that do not acknowledge this client ID, before showing an authorization link. Verification must remain on the configured origin at `/cli/authorize`.
- `POST /api/cli/device/token` with `{deviceCode}` returns `{error:"authorization_pending"}` or `{token}`. Never log the device code, token or model key.
- Authenticated `GET /api/paastacode/connection` returns `{account:{id,tenantId,name,balanceToman},models:[{id,name,supported_parameters,context_length,max_output_tokens,input_toman_per_million,output_toman_per_million}]}`. The account token is sent as a Bearer header.
- Authenticated `POST /api/paastacode/connection` with `{dailyLimitToman}` returns `{key,dailyLimitToman}`. `DELETE` revokes only the requesting device's token and linked key, including a legacy or downgraded token; it never accepts a target identity from the request. The client keeps the AI key outside renderers.
- Inference uses OpenAI-compatible `/api/ai/v1` with that AI key. Prices come from Paasta and money is toman. The Go page is an editorial preference source only.
- Authenticated `GET /api/paastacode/sessions` returns `{sessions:[{id,title,revision,updated_at}]}` for the current user; `GET ?id=UUID` returns one with its snapshot. `PUT` accepts `{id,title,revision,snapshot:{version:1,messages:[{role:"user"|"assistant",text}]}}`; `revision` is zero for a new record or the last acknowledged revision. A conflict returns HTTP 409; successful writes return `{id,revision}` and are read back. `DELETE ?id=UUID` removes one.

The service must enforce user and tenant ownership, role and scope checks, bounded snapshots, encrypted storage, atomic audit, revision conflicts and idempotent key provisioning. A public client is never an authorization boundary. Account tokens must grant only the PaastaCode scopes. The backend was deployed on 2026-10-12; isolated synthetic accounts verified the public HTTPS device flow, model-key lifecycle, encrypted save/readback, retry/conflict behavior and tenant isolation under the production application role. This acceptance did not perform paid inference.

## Deployment integration

New clients launch a per-workspace independent broker via `connectWorkspace`; closing a desktop window, extension host or CLI attachment does not own or terminate it. Registry and engine credentials remain in the protected OS-user state directory. Explicit `paastacode stop` uses the authenticated shutdown endpoint. Account-file changes are detected and account mutations are serialized with snapshot uploads; replacing a grant stops the old engine before another account can use it. Clearing an old grant preserves a newer credential file written by another client. Desktop distributions unpack broker/web assets and launch their own Electron executable in Node mode, so a system Node installation is not required. An older broker is reused safely until explicitly stopped; it is not silently killed during upgrade.

The local broker's `features.backgroundSync:true` enables opt-in per-conversation backup. `GET /api/sync?id=ses_ID` returns only enabled/paused/reason, last-save time, cloud ID and revision. `POST /api/sync` requires `{id,enabled:boolean}` for an owned local session. The broker uploads changed user/assistant text only while the engine is idle, serializes manual/background uploads, pins the initiating identity/token, and verifies readback. Network retries retain the same ID/revision for idempotency; conflicts or remote deletion pause uploads. `POST /api/save` with `{id,copy:true}` explicitly creates an independent cloud copy without overwriting the old record. Restored local sessions retain their original cloud ID/revision, while tool/file/process state is not replayed. Automatic backup requires the local broker to remain running; it does not imply hosted execution or migration of active local processes.

Authenticated `GET /api/paastacode/devices` returns `{devices:[{id,name,device_client_id,created_at,last_used_at,expires_at,revoked_at,current}]}` for the requesting user's PaastaCode grants in the current tenant, capped at 100. It excludes ordinary CLI/API grants, token hashes, prefixes and keys. `DELETE ?id=UUID` requires write scope and current role; an absent or foreign grant returns `{ok:true,revoked:false,current:false}`. Owned revocation atomically revokes the token, linked managed AI key and records one audit; retries do not add audit. The local broker advertises `features.deviceManagement:true` and stops execution/clears login after current-grant revocation. It attempts to revoke this local installation's separately consented deployment grant too; a network failure is reported and preserved for retry. Conversations and workspace files remain. Device listings cannot terminate another user's connection, even within the same tenant.

Individual conversation reads advertise `features.conditionalDelete:true`. The new UI must not enable deletion without this acknowledgement. Conditional deletion uses `DELETE /api/paastacode/sessions?id=UUID&revision=N` with the revision just reviewed; a newer revision returns 409 without deleting. The user lock, row lock, removal and audit are atomic. A missing or already deleted record returns `{ok:true,deleted:false}` without duplicating audit or exposing a foreign account's record. Raw `DELETE ?id=UUID` remains compatible with legacy callers. Export is an explicit browser download of `{version:1,title,messages:[{role,text}]}`; connection and tool metadata are omitted. Retention is manual deletion with a 200-record account limit; background sync is not yet enabled.

The hosted UI origin is exactly `https://code.paasta.cloud`. Local servers reject this origin unless started with `--hosted`; opted-in CORS allows only GET/POST/DELETE and Authorization/Content-Type, never cookies. Every operation still requires the per-workspace capability. The hosted asset route is a fixed allowlist and cannot expose local state, tokens or private platform APIs. Pairing stays in the URL fragment/browser session, and the fragment is cleared before API requests. Supporting browsers request loopback-network permission; denial retains the pairing form and an actionable error. The published service currently supports local execution.

The draft cloud picker uses browser-session cookies on same-origin `/api/paastacode/workspaces` routes. List responses include owned rows and public account identity/balance. Subsequent catalog, quote, lifecycle and runtime requests carry `X-PaastaCode-Owner: userId:tenantId`; the server rejects a changed account. Runtime paths are `/api/paastacode/workspaces/:id/runtime/:path`, without Authorization capabilities or loopback permission. Selected workspace metadata and pending quote tokens are tab-scoped; the picker verifies current ownership and readiness before opening a saved selection. Ambiguous confirmations retain the same operation for explicit retry, including after reload. Orders remain unavailable until the service enables a pinned runtime image; production hosted execution is not yet released.

Deployment is a separate device connection: `clientId:"paastacode-deploy"` must be acknowledged by the server and explicitly reviewed on the Paasta authorization page. Its 30-day token grants only `paastacode:read`, `paastacode:write`, `projects:read`, `deployments:write` and `logs:read`. It must match the base account's user and tenant. `GET /api/paastacode/identity` returns only `{id,tenantId}` after current role/scope checks.

Paasta's `/api/mcp` JSON-RPC endpoint supplies the authoritative project/log/Git-deployment tools. The local stdio broker stores no credential in model configuration and turns mutations into one-use human review requests. Source upload uses the shared MIT Paasta CLI: `--dry-run --hash --json` computes the exact archive hash; approved execution passes `--source-sha256`, `--no-env`, `--no-addons` and `--detach`. A changed source or price fails closed. Deployment observation uses `/api/projects/deploy/:id`; ambiguous mutations are never automatically replayed. Resource selection for new Compose storage remains a completion gate.

## Model workflows and project import

`features.modelWorkflow` enables `GET /api/workflow?id=ses_ID` and optional `phase:plan|build`, `executionModel`, `restart:boolean`, `executePlan:boolean` on `POST /api/prompt`. Missing phase preserves legacy build behavior. Models must exist in the live paid, tool-capable Paasta catalogue with valid prices; free flags/names/IDs and zero-priced or unpriced models are excluded in every client and the account catalogue. Requests serialize with access changes and account mutations. Restart validates before aborting, waits for idle and sends a continuation; it never mutates an in-flight provider stream. Planning uses `paasta-plan` and persistent account/workspace/session read-only permissions. Full Access polling and permission replies cannot promote a managed plan. Execute-plan requires a completed, error-free planning assistant text and reuses its session context. Model choices persist locally; they are not part of the cloud text snapshot. Direct engine TUI calls do not configure this broker workflow.

`features.automaticWorkflow` accepts `autoExecute:true` with `phase:plan` and an eligible `executionModel`. The broker waits for a new completed planning answer, revalidates the account and execution model, persists a handoff intent and submits once to the same session. Closing a browser does not own/cancel that transition. Abort cancels the pending handoff, including while grant revalidation is waiting. An uncertain submit acknowledgement fails closed without replay; startup converts a persisted `handoff` to `interrupted`, visible with an explicit review-and-continue action. Automatic defaults (`state.workflowModels`) use a named role preference policy and an executor cheaper in both input/output rates (strictly cheaper in at least one). Missing compatible roles return null rather than promising savings. Callers may choose an explicit eligible pair. Prices are per actual token use, not a guaranteed task total. CLI exposes the same path with `ask --auto --model=PLANNER --execution-model=EXECUTOR --text=TEXT`.

`features.projectImport` enables `POST /api/import/preview` with `{source:codex|claude|cursor,rules?:boolean,text?:string,format?:text|jsonl}`. It reads only fixed root rule paths in the already selected workspace, rejects outside/symlinked files, bounds file counts and text, and never imports executable configuration. No arbitrary server-side source path is accepted. The result contains selected files, normalized text messages and an opaque account-bound token expiring in ten minutes. `POST /api/import` with `{token}` creates a new local text-context session; digest-based retries in the same account/workspace reuse it. Capability, configured account, origin and account revision checks apply. No inference, cloud upload or source mutation occurs on import. Text is injected with the next explicit prompt. Codex response-item messages and Claude user/assistant JSONL messages omit tools, credentials and metadata; Cursor accepts text/Markdown exports. A caller-provided text may itself contain sensitive information and is displayed for review before user confirmation.

## Workspace ZIP export (draft)

`POST /api/export` with `{}` starts one read-only archive of the broker's fixed workspace. It requires a signed-in Paasta account, an idle engine and no Git write. No caller-selected path is accepted. The response contains `id`, `name` and `chunkBytes`.

`GET /api/export?id=ID&offset=N` returns `{offset,nextOffset,data,sha256,done}`. `data` is base64, at most one MiB decoded. Verify its SHA-256 before writing; advance only to `nextOffset`. The last chunk remains repeatable after an uncertain response. Older or out-of-order offsets and other account identities are rejected. Completion is reported only after the archive process exits successfully. `DELETE /api/export?id=ID` cancels it. Logout, broker shutdown and two minutes without requests also stop the worker. Project mutations and automatic permission grants are held during an active export. These routes are in the private cloud allowlist; existing account, tenant, paid-period and ready-runtime checks still apply.

The streaming ZIP includes Git history, ignored files, project environment files and empty directories. It omits symlinks, special files, named `.paastacode`/`.paasta`/`.ssh` stores, and the broker's configured private account directory. Archive paths reject Windows traversal/ADS forms. Go `os.Root` pins filesystem access inside the opened workspace, with root-identity checks and per-file change detection. The archive is not an atomic filesystem snapshot; external edits can require retry. No temporary full archive is stored on the project's disk, and the broker retains only the current bounded chunk and retry window. The archive can contain the customer's project secrets and must only be delivered to that owner.

The hosted picker offers a download for ready, paid workspaces. It starts the broker export and checks its first bounded chunk before opening the native browser download at `GET /api/paastacode/workspaces/WORKSPACE/export?id=TRANSFER&owner=USER:TENANT`. That handler streams verified chunks without buffering a complete ZIP, rechecks the current account at every chunk, and cancels the cursor after completion or disconnect. Browser feedback reports download initiation, not successful file receipt. A failed preparation cancels the cursor so project edits can continue.

The Go archive helper requires Go 1.27.2 to build. Its local `workspace-export PATH` command does not log in, contact Paasta or run the update checker. Native release CI checks the compiled helper against the broker output byte-for-byte. Recovery while a cloud workspace is suspended and live hosted rollout acceptance remain unfinished; this protocol is not a claim of public hosted export availability.

The hosted hub reads saved conversations through authenticated same-origin `GET /api/paastacode/sessions[?id=UUID]` before a runtime is selected. It sends `X-PaastaCode-Owner: USER:TENANT`; the server rejects a mismatched expected account before reading data. Preview and JSON export do not require a workspace; continuing, deleting and other runtime operations still use the selected owned runtime. Empty/non-JSON responses return a recoverable Persian message instead of a JSON parser error. The public hosted server must expose GET only on this path.
